# チャット読み上げの音声逐次処理設計

2026-10-15 CO。状態: **全文／逐次の切替と別入力ウィンドウを実装。実時間で途切れなく合成する性能条件は未達**。

後続修正で、発話ごとのVoiceDesignから音声変換と共通の参照声によるBaseの話者固定へ変更し、入力中の全文先行合成を追加した。以下は当初の逐次設計と当時の計測であり、現行の操作と検証は[固定話者・先行合成の記録](evidence/studio-speech-fixed-draft-2026-10-15/README.md)を参照する。未入力の言葉の推測は行わない。

2026-10-16に、短いコード履歴だけで毎回復号をやり直す方式による途中の低音化を再現した。現行版は注意機構・因果畳み込みの状態を連続保持し、参照全体を一度準備した状態を発話ごとに複製する。[原因・修正・全コード復号との比較](evidence/studio-speech-register-2026-10-16/README.md)。

同日の途切れ修正で、固定1秒の開始条件を文章長・同程度の長さの過去の読み上げ速度・今回の生成区間の中央値に応じた余裕へ変更した。生成側でPCMを作った時刻を使い、ホストの受信待ちを速度と取り違えない。開始時に8秒を超える量が必要なら既存の120秒上限内のRAMで準備する。終了時の短い後処理PCMと完了通知は一緒に扱い、保留PCMを渡し終える前にリングの終了を立てない。予想外の不足では末尾5msと再開を滑らかにする。以下の固定1秒の記述・初期性能値は当時の方式で、現行の比較は[途中・語尾の途切れ修正](evidence/studio-speech-continuity-2026-10-16/README.md)を参照する。

後続の実装依頼に合わせ、ユーザーが明示的に選択する逐次再生を追加した。以下のS0〜S5と性能基準は当初の設計であり、実装完了をもって連続配信向けの性能達成とは扱わない。通常は従来の全文生成後を使い、逐次は生成済み部分から再生して不足時に待つ。

実装は`SpeechPreferences.delivery`（省略時`whole`）、固定ソースhashを確認する[speech_stream_backend.py](../tools/voice-engine/speech_stream_backend.py)、8KiBヘッダー＋最大1秒の生PCM、8イベントの受信キュー、8秒の再生リング、1秒の開始／再開バッファを使う。24→48kHz変換・音質調整・ピーク保護は区間をまたいで保持し、発話の両端だけフェードする。発話途中の全文方式への自動切替は行わない。

WindowsではSciPyの初回拡張読込と別スレッドのstdin待機が競合したため、モデル初期化後に中断コマンドの監視を開始する。初期化中の停止は3秒の待機後に所有する子プロセスだけを終了する。通常の逐次生成は協調停止し、モデルを次回へ保持する。

別入力ウィンドウは`/speech-input`で専用UIだけを起動し、音声サービス・モデル・プロジェクトストアを複製しない。token、要求ID、プロジェクトIDでコマンドを検査し、同一要求の重複実行と切替前のプロジェクトへの送信を防ぐ。PCMはメイン側の既存の口パク経路だけへ送り、入力ウィンドウには送らない。

実機では音声3.60秒に生成15.17秒、生成開始から最初のPCM2.71秒、再バッファ2回、協調停止537msだった。最初のPCMの時点は再生開始ではなく、初回モデル読込15.25秒と再生バッファは別途必要。[実装の検証と限界](evidence/studio-speech-streaming-2026-10-15/README.md)を参照。

ユーザーの優先順位は「音声合成側の逐次処理を先に対応し、その後に入力中の先行合成を検討する」。この文書は前者の実装範囲、採用判断、通信、再生、停止、口の同期、検証条件を定める。

## 1. 今回決める方式

**送信時に文章全体と文脈を一度に渡し、生成できた音声から順番に再生する。** 文の意味を判断する入力と、波形を取り出す単位を分ける。全文を使う現在の抑揚の条件を維持しながら、全音声の完成待ちを減らす。

| 項目           | 方針                                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------------------- |
| 読み上げる内容 | ユーザーが送信した文章そのもの。自動の返事は作らない                                                     |
| モデルへの入力 | 確定した全文、声の説明、場面・読み方、直前3件の完了した発話を開始時に固定                                |
| 音声の出力     | 一つの発話の生成を継続し、その途中からPCMを取り出す                                                      |
| 第一候補       | 既存のWindowsネイティブ環境、Qwen3-TTS VoiceDesign 1.7Bを維持するアダプター                              |
| 成立条件       | 最初の音が早いことに加え、その後も再生に間に合うこと                                                     |
| 停止           | 再生をすぐ止め、生成を協調的に中断する。通常停止ではモデルを再利用する                                   |
| 互換経路       | 現在の全文完成後の再生を残す。発話途中の自動再生成・再読上げは行わない                                   |
| 今回の範囲外   | 入力途中の推測、下書きの先行合成、文字差分の追加、送信前の発話、送信待ち行列、新しい声のモデルの自動選択 |

句点で文章を分けて独立に合成する方式は、今回の逐次処理の完成条件に含めない。声や抑揚が文ごとに変わる問題を避け、一つの生成状態を維持する。

## 2. 現状の確認結果

| 場所                                                               | 現在の処理                                                           | 変更が必要な理由                             |
| ------------------------------------------------------------------ | -------------------------------------------------------------------- | -------------------------------------------- |
| `tools/voice-engine/speech_worker.py`                              | `generate_voice_design()`から全波形を受け、一時WAVを書いて完了を通知 | 最初のPCMが全生成終了まで届かない            |
| `tools/voice-engine/speech.py` の `SpeechJob`                      | WAVを読み、全文を一括で後処理                                        | チャンク受信と状態を持つ後処理が必要         |
| 同 `SpeechPlayer`                                                  | 完成した配列を再生                                                   | 生成中も追加できる有限リングが必要           |
| `tools/voice-engine/studio_speech.py`                              | `speechReady`を受けて再生開始                                        | 生成中と再生中が重なる状態を扱う必要がある   |
| `host.py`、Tauri、`VoiceService`、`packages/audio/src/playback.ts` | 最終48kHz PCMとDAC時刻を口の解析へ渡す                               | この経路を維持し、生成終了で先に口を閉じない |

導入済みの`qwen-tts 0.1.1` / `transformers 4.57.3`では、公開メソッドは音声コードの生成終了後に波形を返す。`non_streaming_mode=False`へ変えるだけでは逐次入出力にならない。現物の確認対象とSHA256は[ソース監査記録](studio-speech-streaming-source-audit.json)に保存した。[公式の呼び出し口](https://github.com/QwenLM/Qwen3-TTS/blob/main/qwen_tts/inference/qwen3_tts_model.py)にも、その引数だけで真のストリーミングにはならない旨が記載されている。

導入済みの内部実装では、Talkerの各生成ステップで16コード群のフレームが組み立てられ、最終的にはそれらを集めて復号する。12Hz系の波形デコーダーには、過去のコードを付けて復号し、その過去部分を切り除く処理がある。ただし、それを小さい単位で呼んだ場合の速度・境界品質は、このPCでは未検証。[公式のモデル内部](https://github.com/QwenLM/Qwen3-TTS/blob/main/qwen_tts/core/models/modeling_qwen3_tts.py)、[公式デコーダー](https://github.com/QwenLM/Qwen3-TTS/blob/main/qwen_tts/core/tokenizer_12hz/modeling_qwen3_tts_tokenizer_v2.py)。

### 性能の出発点

[前回の実機結果](evidence/studio-speech-2026-10-15/native-speech.json)は、RTX 4050 Laptop 6GBで初回読み込み17.28秒、生成12.90秒、音声3.12秒、最大VRAM約4087MiB。生成時間を音声時間で割ったRTFは約4.13。

これは一つの短文の全体計測であり、常駐後の連続生成速度や最初のPCMができる時刻を測ったものではない。まず段階ごとの実測を取る。

仮に逐次化後も音声末尾ができるのが開始から12.90秒後で、3.12秒の音声を通常速度で途切れず再生する場合、再生開始には約9.78秒の待ちが必要になる。これは音声末尾ができる時刻を仮定した時間関係であり、逐次化後の性能予測ではない。**チャンクを送れるだけで低遅延配信が成立したとは扱わない。**

## 3. 合格条件と計測

以下の数値は**設計上の目標**。未達のものを達成済みとして表示・記録しない。

| 指標             | 定義                                                              | 本番採用の目標                                      |
| ---------------- | ----------------------------------------------------------------- | --------------------------------------------------- |
| 最初のPCMまで    | モデル常駐時の要求受理から、再生可能な最初のPCMがホストへ届くまで | p50 1秒以下、p95 2秒以下                            |
| 最初の実出力まで | 要求受理から、先頭PCMのDAC開始時刻まで                            | p95 2.5秒以下。上の指標と分ける                     |
| RTF              | 生成・逐次復号を含む所要時間 / 生成音声の長さ                     | 常駐後p95 0.8以下を目標。初回読み込みを別記         |
| 生成の間隔       | 隣接PCMの到着間隔、累積生成秒数、リング残量の時系列               | 平均RTFが良くても、バッファを使い切る停止がない     |
| 再生             | 初回の準備完了から発話末尾まで                                    | 試験中の不足・重複・欠落0                           |
| 停止             | 停止要求受理から最後の可聴出力まで                                | p95 200ms以下を目標。既に機器へ渡した区間も含む     |
| 協調停止         | 生成側が取消を認め、次の要求を受けられるまで                      | p95 1秒以下を目標。モデルの再読込0回                |
| 口の時刻         | ホストが通知した最終PCMと、口解析へ渡すPCMの対応                  | サンプル範囲とDAC時刻が一致。実機の見た目は別途確認 |

RTFだけで開始バッファを決めない。累積PCM秒数を`A(t)`、再生開始を`t0`とすると、再生中は`A(t) >= t - t0`を満たす必要がある。実際には復号・DSP・機器の余裕も見込む。到着のばらつきと残量を測り、先頭300〜800ms程度の範囲を候補として調整する。数秒以上をためないと成立しない場合は、先に合成側の速度を改善する。

## 4. 合成バックエンド

### 4.1 Windowsネイティブのアダプターを第一候補にする

新規候補`tools/voice-engine/speech_stream_backend.py`に、上流の固定版に対応した小さいアダプターを置く。既存の`.venv-voice-design`や元liverVoiceChangerのファイルを直接変更しない。モデル重みと音声設定も維持する。

1. 現在と同じ全文・指示の組み立てと全文を事前に条件付けするモードを使う。音声コード生成のKVキャッシュを、一つの発話の間で継続する。
2. 外側のTalkerが**全16コード群を揃えたフレーム**を取り出す。Transformersの通常のテキスト用streamerは、波形に必要な全コード群を渡すとは限らないため、そのまま使わない。
3. 最初はフレーム取得の試作で、prefillの除外、コード群の順序、EOS、終端の一フレーム、固定seedの再現を検証する。その結果をもとに、コード取得と停止判定の箇所だけを明示した生成アダプターにする。
4. フレームを一定数ため、波形デコーダーへ渡す。すでに復号済みの過去コードを文脈として含め、その部分のPCMを除去して新しい区間だけを出す。
5. 全発話のhidden statesや全波形を集め続ける処理は外す。発話単位のKVキャッシュは既存の入力・最大生成長で上限を持たせる。

アダプターは、監査した上流のバージョン・ソースhash・モデルrevision・構造を照合してから有効化する。不一致では、再生を始める前に現在の全文方式へ戻し、その理由を診断へ出す。依存更新時には再検証する。取り込むコードの出典・ライセンス・変更点を記録する。

### 4.2 波形を取り出す単位

初期の比較候補は、先頭2 / 4 / 8フレーム、以後4 / 8 / 12フレーム。音声1フレームの長さは、実際の`decode_upsample_rate`と出力sample rateから求める。導入済みコードの既定値1920サンプル / 24kHzなら80msなので、4フレームは320msとなる。モデル名の「12Hz」から固定換算しない。

過去文脈は上流の`left_context_size=25`を比較の出発点にする。小さいブロックでも同じ品質が出ることを保証する値ではない。必要な文脈長、境界の差、演算の重複を測って決める。各回で発話の先頭から全コードを復号し直す方式は、発話が長いほど負荷が増えるため採用しない。

初期実装はGPUモデルを一つにし、一つの所有スレッドで生成とブロック復号を順に扱う。IPC書込みは別の有限キューへ渡す。別GPUモデルの並列ロードや複数CUDA streamによる競合を最初から加えない。

### 4.3 速度改善と代替候補の扱い

最初にprefill、Talker、残りのコード群の生成、波形復号、GPU→CPU転送を分けて測定する。全hidden statesの保持、不要なGPU同期、細かすぎる復号単位を先に調べる。固定長の残余コード生成やGPU実行の最適化は、固定seedのコード比較と実機計測を通してから採用する。

既定の声・抑揚・精度・モデルサイズ・サンプリング条件を黙って下げない。変更が必要なら比較結果とともに別の選択肢として扱う。

現在のvLLM-Omni公式資料には、VoiceDesignを含むQwen3-TTSのPCM逐次出力がある。[公式資料](https://docs.vllm.ai/projects/vllm-omni/en/stable/user_guide/examples/online_serving/text_to_speech/#qwen3-tts)。ただしvLLMの公式要件はLinuxで、WindowsではWSL等が必要とされる。[動作環境](https://docs.vllm.ai/en/stable/getting_started/installation/gpu/)。このPCの6GBでの成立は未確認なので、ネイティブ経路が性能目標を満たさない場合の比較候補とする。WSL・別サーバー・新しいモデルの導入を、この設計整理だけで行わない。

## 5. 全体の経路

```mermaid
flowchart LR
  UI[確定した全文・場面・履歴] --> Host[Pythonホスト]
  Host --> Gen[常駐Qwen worker]
  Gen --> Codes[音声コードの継続生成]
  Codes --> Decode[過去文脈付きブロック復号]
  Decode --> IPC[有限のPCM通信]
  IPC --> DSP[状態を持つ48kHz変換・声質・フィルタ]
  DSP --> Ring[有限の再生リング]
  Ring --> WASAPI[専用音声スレッド・最終出力]
  WASAPI --> Device[配信先の音声機器]
  WASAPI --> Analysis[最終PCMとDAC時刻]
  Analysis --> Tauri[Tauri Channel]
  Tauri --> Mouth[既存の口の連動]
```

音声機器への出力はPythonのWASAPIのままにする。WebViewへ送るのは、実際に再生する最終PCMの口解析用コピーだけ。生成した24kHz音声の本体をTauriやブラウザ経由で再生し直す経路は追加しない。

## 6. workerとホスト間の通信

### 6.1 識別子とフレーミング

新しいworker通信はバージョン付きにし、`hello`で`streamingPcm`と`cancelKeepModel`の能力を確認する。既存のWAV用通信と混在させない。

要求には`utteranceId`、接続を作り直すたびに変わる`epoch`、全文・文脈・声・設定・seedのスナップショットを持たせる。音声と完了通知の両方で識別子を照合する。

| 通知              | 主な内容                                                                 |
| ----------------- | ------------------------------------------------------------------------ |
| `streamBegin`     | 識別子、実際のsample rate、mono、`f32le`、モデルrevision                 |
| `pcm`             | 識別子、連番、累積`startSample`、`frames`、`byteLength`に続くバイナリPCM |
| `generationEnd`   | 識別子、総サンプル数、生成・復号の計測値。再生終了の意味には使わない     |
| `cancelled`       | 識別子、取消確認、モデルを再利用できるか                                 |
| `generationError` | 識別子、エラー、モデルを再利用できるか                                   |

制御は改行JSON、PCMは小さい改行JSONヘッダーと直後の固定長バイナリにする。ヘッダー上限8KiB、PCMは1メッセージ最大1秒分とし、上限を検証してから読む。初期対応は24kHz mono float32、1秒で96,000バイト。長さ・有限値・連番・サンプル開始位置の連続性を検証する。短いread/write、途中EOF、過大な長さ、末尾だけ短いPCMも扱う。ログはstderrへ分ける。

バイナリPCMの上限はworker専用の通信契約であり、Tauriの既存128KiB JSON上限を変更する理由にはしない。Tauri側の48kHz・10ms解析通知は既存形式を保つ。

### 6.2 待ち行列と取消

要求受信スレッドは推論と分け、生成中・通信待ちでも取消を受け取れるようにする。推論要求は実行中1件、未実行0件から始める。将来の先行合成は別のスケジューラーで扱う。

PCMキュー・リングは秒数で上限を決める。初期の上限候補は各4秒。高水位では生成側へ待ちを返し、音声コールバック外で待つ。最大チャンクと復号の作業領域にも上限を持たせ、同じサンプルを保持する領域を含めた合計使用量を計測する。

音声本体は満杯を理由に捨てない。口解析だけは既存の有限キューで古い通知を捨てられる。キュー待ちでも取消とホスト切断を検出する。取消後の旧識別子のPCMや完了通知は、新しい発話へ取り込まない。

## 7. 状態を保つ音声処理と再生

### 7.1 チャンク間の連続性

新規候補`SpeechStreamProcessor`を一つの発話につき一つ作り、次をチャンク間で保持する。

- 24kHz→48kHz変換のFIR履歴・位相・未出力サンプルと遅延補正。
- `ToneProcessor`、`FilterChain`、`PeakGuard`の内部状態。
- 累積の入出力サンプル位置、末尾のフェード用の保留区間。

`resample_poly()`を各チャンクへ独立にかけたり、毎回フィルタを作り直したりしない。リサンプラーは連続入力と最終flushを扱い、固定比2倍の区間でサンプルが重複・欠落しない契約にする。群遅延の扱いを一括処理との比較で確かめる。

フェードは発話の先頭と末尾だけに付ける。末尾用には5ms程度を保留して`generationEnd`で確定する。全チャンクの両端へフェードを付けて継ぎ目を隠す方式は使わない。通常の無音や息を、入力用の発話ゲートで切らない。

声の説明・場面・声質・フィルタは発話開始時の設定で処理する。Muteと停止だけを再生中も即時反映する。設定変更は次の発話から有効にする。

### 7.2 再生リング

`SpeechPlayer`を、配列の再生から有限リングの再生へ拡張する。生成終了フラグと未再生サンプル数を別に持つ。

COM初期化、audio mutex、ストリームの作成・開始・停止・破棄を同じ専用音声スレッドで行う。既存の修正を維持する。コールバック内では推論、復号、IPC、ディスクアクセス、キュー待ちを行わず、音声の取得・Mute/停止のランプ・最終PCMの有限コピーに限定する。

初回は開始に必要な分をためてから再生する。生成未完了なのにリングが空になった場合、初期の本番方針は「残りを無音で埋めて出力を止め、再生不足を表示し、その発話の生成も取り消す」。語中へ長い無音を入れて何度も再開する動作を正常扱いしない。試作段階では不足の再現と計測のためのモードを分ける。

## 8. 状態と口の同期

現在の単一の状態だけでは、生成終了と発話終了を区別できない。`VoiceState`の既存外側状態は保ち、`speech`に実行時情報を加える案とする。

```ts
type SpeechPhase = 'idle' | 'preparing' | 'buffering' | 'playing' | 'draining' | 'cancelling' | 'error';
// 実装時に @app/contracts と整合させるための設計上の形
type SpeechRuntime = {
  utteranceId: string | null;
  phase: SpeechPhase;
  generationDone: boolean;
  bufferedMs: number;
  history: SpeechHistoryEntry[];
  resident: boolean;
};
```

`SpeechHistoryEntry`は次節の完了・途中停止を区別する実行時の履歴項目。現在の`string[]`からの変更は画面・サービス・fake・テストをまとめて更新する。

| 内側の状態 | 外側の状態 | 意味                                       |
| ---------- | ---------- | ------------------------------------------ |
| preparing  | loading    | モデルを読み込み中                         |
| buffering  | priming    | 生成開始済み。再生に必要な量を準備中       |
| playing    | running    | 生成と再生が進行中                         |
| draining   | running    | 生成済み。リングと機器内の音声を再生中     |
| cancelling | stopping   | 以後のPCMを拒否し、生成の停止確認中        |
| idle       | stopped    | 最後のDAC区間が終わった、または取消完了    |
| error      | error      | 当該発話は終了。自動で全文を再読上げしない |

`generationEnd`だけでは`stopped`へ移らない。実際の最終PCMの末尾DAC時刻まで`running`を維持する。再生不足・Mute・停止時には実際に出力したゼロを口解析へ渡し、口を閉じる。

`VoicePlayback`の48kHz PCM・連番・DAC時刻の契約を維持する。キューへ追加した時刻やGPUで生成できた時刻を、発話の時刻として通知しない。既存の同期微調整と、カメラの顔・目の追跡を維持する。

## 9. 取消、常駐、履歴

### 9.1 停止とモデルの解放

停止要求では、ホスト側で対象の識別子を無効化し、リングを破棄して短いランプで出力を止める。GPUからの取消応答を待ってから音を止める順序にはしない。WebViewも停止中は旧PCMを拒否する。

workerは外側の生成ステップ境界とブロック復号の前後で取消を確認する。残余コード群の途中で不完全なフレームを出さない。協調停止では、その発話のKV・コード・PCM・DSP状態を破棄し、モデル重みを保持する。次の要求のseedと文脈は新しく初期化する。

取消の期限超過、CUDAエラー、プロトコル破損、ホスト切断では、自身が起動したプロセスと子だけを終了する。モデルを再利用できなくなったことを通知する。GPUが応答しない場合でも、再生停止の操作は先に完了させる。

［読み上げモデルを解放］、マイク変換・WAV変換への切替、実行環境変更、アプリ終了ではworkerを解放する。元liverVoiceChangerとのGPU mutex、audio mutexは維持する。通常停止と明示的な解放の違いを操作説明にも反映する。

### 9.2 途中まで話した文章

現在は生成できた文章を再生開始時に履歴へ追加する。逐次処理では、最後まで話したかを扱う必要がある。

- パネルの履歴は`text`、`delivery: completed | interrupted | failed`を持つ実行時情報にする。
- 完全に再生した発話だけを、次の生成へ渡す直前3件の文脈に使う。全Muteで最後まで時間が進んだものは、文脈の既定では除外する。
- 途中停止・不足・途中エラーは、画面へ「途中停止」「音声エラー」と表示し、全文を話したことにしない。
- PCM位置から実際に読んだ文字数を推測しない。語単位の対応付けは今回の範囲外。
- 下書き・履歴・PCMは次回起動へ保存しない。モデル切替・プロジェクト切替の境界で混ぜない。

モデル解放とプロジェクト切替時には、音声本体のバッファも破棄する。診断に文章本文を必要としない場合は識別子と計測値だけを記録する。

## 10. 画面と計測項目

入力欄と送信操作は維持する。状態表示を「モデル準備中」「音声を準備中」「読み上げ中」「残りを再生中」「停止しています」に対応させる。生成中・再生中も次の文章を下書きできる。処理方式をユーザーが判断する必要がある場合だけ「逐次再生」「全文生成後に再生」を示す。

［音声の計測］には、初回読み込み、prefill、最初のコード、最初のPCM、先頭DAC、生成RTF、到着間隔p95/max、最小/最大バッファ量、不足回数、協調取消時間、GPUメモリの最大値を分けて出す。常駐時と初回の数値を混ぜない。

本番の配信開始前にモデルを準備できる操作は用意するが、プロジェクトを開いただけでGPUを自動占有しない。音声の機器設定は既存のPC側設定を使い、機器別のバッファ調整をプロジェクトへ持ち込まない。初期のチャンク数・開始バッファは検証用設定とし、つまみを増やさず実測で固定する。

S3の模擬PCM試験はS2が未達でも進められる。実際のモデルによる逐次再生を有効にする判断はS2とS5を通ってから行う。文書に列挙した新規ファイルは作業予定であり、この設計整理では実装していない。

既存`VoiceService.speak()`の引数、送信済み文章の保存方針、声・場面のプロジェクト設定は原則維持する。新規の実行状態は`@app/contracts`で定義し、fakeも同じ契約に合わせる。Tauriは現在の制御・最終PCM解析通知を継続し、PCM本体の転送先にしない。契約変更は実装時に`docs/contract-changes.md`へ記録する。

実機検証、開発サーバー、アプリ更新、e2eは`.cache/locks/main.lock`を取得して行う。GPUの試験でも既存の排他を守る。検証用の識別子・プロジェクトの写しを使い、起動中のユーザーのアプリを断りなく閉じない。

## 12. 必須の検証

| 対象         | 確認すること                                                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| コード生成   | 同じ入力・seedで元の全生成と比較。prefill除外、全コード群、EOS、短文、最終フレーム、最大長での打切りを区別                           |
| 音声の境界   | 同じコード列を一括/逐次で復号して比較。各チャンクを重ねて誤差・サンプル数・境界の段差を測る。波形の完全一致を仮定しない              |
| DSP          | さまざまな分割サイズでリサンプル、フィルタ、出力保護の連続性とflushを確認。フェードが内部境界に増えない                              |
| 通信         | 短いread/write、破損ヘッダー、過大なPCM、NaN、欠番、重複、旧epoch、EOF、満杯、ホスト切断                                             |
| 停止         | 初回ロード中、prefill中、残余コード生成中、復号中、キュー待ち、再生中、draining中。停止後に旧音声が復活しない                        |
| 常駐         | 協調停止→即座の新規要求、20回の生成・停止、明示解放、マイク/WAV変換へ切替。重みの重複ロードや残留プロセスがない                      |
| DAC・口      | 生成終了後も末尾まで口を合わせる。MuteのゼロPCM、解析通知の遅れ、バッファ不足で口を閉じる                                            |
| 履歴         | 完了・途中停止・エラー・全Muteを区別し、文脈に未発話全文を混ぜない                                                                   |
| 日本語と抑揚 | 挨拶、疑問、否定が文末にある文、励まし、驚き、長い一文、数文、数字・固有名詞。全文方式と聞き比べ、音切れ・声の揺れ・読み落としを確認 |
| 継続性能     | warm-upを別記し、常駐20発話以上、30秒程度の音声、最大300文字、30分の断続送信で不足・VRAM・RAM・待ち行列を測る                        |
| 実機         | 指定WASAPI機器へのMute出力、両画面サイズ、設定保存、既存マイク変換。配信経路と聴感は利用する出力先で別途確認                         |

最初のPCMが全文生成終了前に届くこと、一定の小さな開始バッファで途切れず再生できること、全文方式に比べて意味・声・抑揚が悪化しないことを、別々の採用条件とする。速度だけを理由に品質低下を合格扱いしない。

途中まで再生済みの発話で逐次処理が失敗した場合は、その場で全文方式を自動再実行しない。次の発話を全文方式へ戻すかを表示し、同じ言葉が二重に配信されることを防ぐ。
