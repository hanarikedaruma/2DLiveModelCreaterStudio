### 指摘（COへ・試験側）：仮カメラの試験の Worker の終わりを待つ時間が短い

- **再現**：COの「同梱モデルを仮カメラで動かし…」の ON/OFF の繰返し（`arm-tracking.at13.e2e.ts` 449〜450行）は、OFF の後 `sleep(800)` で `workers()` が0であることを求める。AT-04 は OFF で推定を止める知らせを送り、推定器を閉じる時間として **500ms 後に Worker を終わらせる**（`tracker.ts` の `terminateDelayMs`）。WebView2 が Worker の終わりを知らせるまでの時間がその後に足される。
- **測定**：CLの e2e ③で OFF から `workers()` が0になるまでを測ると、2回の実行の10回で **1045・720・879・786・696・884・814・815・813・884ms**。800ms を超えたのは10回中7回で、どの回も0になった（最大1045ms）。ON の間は毎回1つだけ。COの最初の OFF の確認（422〜423行、1000ms）も最大の値を超えうる。
- **判断**：製品の不具合ではない（OFF の直後に Pose・手の通知は止まり、Worker は約1秒以内に終わる）。期待値の「0になる」は正しく、待ち方が短い。固定の待ちを延ばすのではなく、上限（例えば2秒）まで0になるのを待ち、かかった時間を結果に残す形にしてほしい（試験を弱めない）。

### 追記：CO v2 の1回目の失敗（OFF の後5秒で Worker が残る）の切り分け

COは試験を「上限5秒まで Worker 0 を待つ」形に直した（AT-13 CO v2）。その1回目（22:02〜22:04）は、繰返しの中の OFF で5秒を超えて Worker が1つ残り失敗し、その後の COの診断の2回は成功した（530・679・617ms、533・630・621ms）。1回目は CL の全 workspace 試験と重なっていたので、同じ負荷の下で16回測った（[測定](../evidence/AT-13-cl/worker-stop-load.json)）：ready の1.5秒後の OFF は523〜713ms、ready の直後の OFF は1108〜1670ms で、全て0になった。CLの負荷なしの10回と COの6回を合わせて32回、5秒を超えた回は無い（最大1670ms）。AT-04 のコードにも、前の Worker を止めずに差し替える道は見つからなかった。1回目に残った Worker が腕の推定のものか（URL）は記録が無く、COが足した診断で再現を待っている。再現したら AT-04 の担当（CL）が直す。
