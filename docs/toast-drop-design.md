# 通知が素材のドロップを妨げないようにする（I-075設計）

2026-10-12 CO。[軽い対応から進める計画](issue-backlog-plan.md)の1件目。同日、ユーザーの実装開始指示を受け、CSS案で実装・検証した。[確認記録](evidence/issue-backlog-2026-10-12/README.md)。

## 解決すること

素材を取り込んだ直後、右下の通知が標準パーツの割り当て枠と重なると、素材を落とせない。通知の4秒の表示が終わるまで待たずに割り当てられるようにする。

## 現行コードで確認したこと

| 場所                                    | 現在の役割                                                                                                                          |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `shell/dialogs.tsx`                     | `.toasts`内に通知を表示する。通知を押すと消える。確認ダイアログとは別のDOM                                                          |
| `shell/shell.css`                       | `.toasts`は右下固定・z-index 110。通知はマウス操作を受け取る                                                                        |
| `modes/modeling/assets/dnd.ts`          | Tauriの内部ドラッグはHTMLのdrag/dropではなくpointerイベント。実際にドラッグが始まると `body` に `dnd-dragging` を付け、終わると外す |
| `modes/modeling/assets/AssignPanel.tsx` | 素材の割り当て枠は `useDropTarget` の `onPointerUp` で素材を受け取る                                                                |

通知がpointerupの対象になるため、その下の枠へ届かない。`dragstart`の監視を追加する案では、現在の内部ドラッグを検知できない。

## 採用する案

ドラッグ中だけ通知をマウスの対象から外す。既存の `body.dnd-dragging` を使い、殻のCSSに規則を足す。

```css
body.dnd-dragging .toasts,
body.dnd-dragging .toast {
  pointer-events: none;
}
```

通知の表示は続ける。HTML要素へのヒット判定が下の割り当て枠に届き、既存のドロップ処理がそのまま動く。通常時は今までどおり通知を押して消せる。

ドラッグの開始判定、payload、枠の割り当て処理、通知タイマーは変更しない。パーツの階層・描画順の内部ドラッグでも同じ規則が効く。

## 他の案との比較

| 案                             | 評価                                                                     |
| ------------------------------ | ------------------------------------------------------------------------ |
| ドラッグ中だけマウス判定を外す | 推奨。既存の開始・終了の印を使い、通知の位置や普段の操作を変えずに直せる |
| 常にマウス判定を外す           | 通知を押して消す既存操作まで失われる                                     |
| キャンバス側へ通知を移す       | 通知に隠れる操作場所が変わる。ドロップを妨げない保証にはならない         |
| 殻で独自のドラッグ状態を持つ   | 既存の状態と二重になる。今回の問題には不要                               |

## 変更範囲

製品コードは `apps/desktop/src/shell/shell.css` の通知の規則が中心。`dialogs.tsx`や`dnd.ts`に機能追加する必要はない。プロジェクト・環境設定・契約の変更は無い。

外部ファイルのドラッグを含む通知全般の再設計は、この内部素材ドロップの修正とは分ける。

## 確認手順と完成条件

1. 確認用モデルで素材を取り込み、通知が見える間に割り当て枠と通知が重なる状態を作る。
2. 素材をトレイから運び、通知が覆っている枠の位置で離す。枠へ割り当てられ、通知のクリックによる消去は起きない。
3. 1回のUndoで割り当てが戻る。複数素材でも既存の割り当て処理が動く。
4. ドラッグ中に別の通知が出ても枠が反応する。表示期限が来た通知は通常どおり消える。
5. ドラッグを完了・Escで中止・pointercancelで中止したあと、通知を押すと消える。通知の無い状態のドロップも変わらない。
6. パーツの階層と描画順のドラッグで、通知の下の落とし先へ届く。確認ダイアログの操作は、このCSSの対象にならない。

1440×1000・800×600の実ブラウザと、Tauri/WebView2の内部ドラッグで確認する。jsdomでクラス名だけを確かめても、重なった要素へのヒット判定の検証にはならない。

ドラッグ中の通知の下で枠が反応すること、終わったあと通知を押せることを完成条件とする。実行した環境と画像・確認結果を課題へ記録して締める。

## 実装と確認（2026-10-12）

設計のCSS規則を追加した。Edgeの1440×1000・800×600と、本物のWebView2の1440×1000・960×600で、実際に通知と割り当て枠を重ねてドロップし、Undoと終了後の通知クリックを確認した。EdgeではEscによる中止も確認。クラス名だけを比較する新しい単体テストは作らず、実際のヒット判定を確かめた。課題は対応済み、インストール版の更新は未実施。
