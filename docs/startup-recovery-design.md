# 起動時の復元を保留・破棄できるようにする（I-071設計）

2026-10-12 CO。[軽い対応から進める計画](issue-backlog-plan.md)の3件目。同日、ユーザーの実装開始指示を受け、3択と世代を限定する破棄を実装・検証した。契約はCC-018。[確認記録](evidence/issue-backlog-2026-10-12/README.md)。

## 解決すること

起動時の「復元しますか？」でキャンセルしても自動保存が残り、毎回同じ確認が出る。後で復元するために残す操作と、もう不要な自動保存を破棄する操作を区別する。

キャンセルをそのまま削除の意味に変えると、Escやいつもの操作で作業を失う。3択を明示する案を推奨する。

## 現行コードで確認したこと

- `apps/desktop/src/project/actions.ts`の`recoverOnStartup`は、前回の保存先と未保存用フォルダを候補にし、`autoSaver.findRecoverable`で見つけた最新の自動保存を読む。
- `dialogs.confirm`はbooleanを返す。falseなら次の候補へ進むだけで、ファイルを消さない。
- `packages/io/src/project/autoSaver.ts`は`backups/autosave-*.json`を世代として管理する。最新1個だけを消すと、次の起動で古い世代が再び復元候補になり得る。
- 保存先のあるプロジェクトの`assets/`は本体と自動保存で共用する。未保存用のフォルダも素材を含む。
- `AutoSaver`の契約には`start`・`stop`・`findRecoverable`だけがある。復元候補を破棄する口は無い。

## 操作の仕様案

文面の案:

> 前回、保存していない変更が残っています（プロジェクト名）。復元しますか？
> 「自動保存を破棄」を選ぶと、この作業の自動保存を消します。

| 操作           | 結果                                                               | 次回の起動                                       |
| -------------- | ------------------------------------------------------------------ | ------------------------------------------------ |
| 復元する       | 現在と同じ復元処理。復元したプロジェクトは変更ありにする           | その後の保存・自動保存に従う                     |
| 後で決める     | 自動保存を残し、次の候補へ進む                                     | 同じ候補が残っていれば、また聞く                 |
| 自動保存を破棄 | 表示した候補と、それ以前の対象の自動保存世代を消し、次の候補へ進む | 新しい自動保存が無ければ、その作業をまた聞かない |
| Esc            | 「後で決める」と同じ                                               | 残っていれば、また聞く                           |

最初のフォーカスは「復元する」に置く。破棄を初期選択にしない。Enterはフォーカス中のボタンの操作とし、汎用のEnter処理で別の選択へ置き換えない。破棄の意味を同じダイアログ内に書き、連続する確認は増やさない。

候補が複数ある場合は今と同じ順に確認し、1つ復元できたら終了する。保留・破棄を選んでも、別の候補には同じ選択を自動適用しない。

## 自動保存を破棄する範囲

削除するのは、IO側の`isAutosaveName`で確認でき、対象プロジェクトの`backups`にある自動保存JSONだけ。

- 表示した候補より古い世代も対象にし、古い作業の確認が次々に現れることを防ぐ。
- `project.json`、素材のPNG、通常の保存バックアップ、別のプロジェクト、フォルダ全体は削除しない。
- 未保存用のフォルダでも同じ規則にする。残る素材・空フォルダの掃除は今回の復元確認とは分ける。
- `actions.ts`から`fs.remove(dir)`でフォルダごと消す作りにはしない。自動保存のファイル名と世代の判断はIO側にまとめる。

破棄は作品のUndoでは戻せないため、ボタンに対象が自動保存であることと消去されることを明示する。今回は実際の自動保存を操作せず、実装後の確認には専用のテストフォルダを使う。

## 契約と処理の案

### 3択のダイアログ

`shell/dialogs.tsx`の`Dialogs`に、選択肢を返す口を追加する。

```ts
choose<T extends string>(
  message: string,
  choices: readonly { value: T; label: string }[],
): Promise<T | null>;
```

復元処理は`restore`・`later`・`discard`を渡し、Escの`null`は`later`として扱う。既存の`confirm`・`prompt`はそのまま使う。選択型のrequestと描画・answerの分岐を足し、既存のダイアログのキューに載せる。

選択肢の先頭とEnterを無条件に結び付けない。押されたボタンのvalueを返す。Dialogsを実装・注入しているテストの代替も更新する。

### IO側の破棄処理

`AutoSaver`へ次の口を追加する案とする。契約変更番号は実装時に採番する。Projectの保存形式やschemaVersionは変えない。

```ts
discardRecovery(
  dir: string,
  expectedPath: string,
): Promise<'discarded' | 'changed'>;
```

`expectedPath`は画面から任意に受け取るパスではなく、その候補の`findRecoverable`が返し、確認文のために読んだパス。IO側で対象の`backups`直下の自動保存名であることを検証する。

処理の条件:

1. 起動時の候補を処理している間は、このインスタンスの通常の自動保存を開始しない。破棄中に同じインスタンスが新しい世代を書かないようにする。
2. 表示した候補がまだ最新の復元対象か再確認する。候補が消えた・変わった場合は`changed`を返し、その候補を取り直す。新しい作業を古い確認への返答で消さない。
3. 削除直前に世代の一覧を取得する。その一覧のうち、表示した世代以前の自動保存名だけを削除対象に固定する。表示後に追加された新しい世代は対象にしない。
4. ファイル単位で削除する。判定には現行の自動保存の並べ方を共用し、パスの文字列の前方一致だけで対象ディレクトリを判断しない。
5. 削除したあと復元候補を再確認する。新しい世代があれば`changed`として取り直し、確認する。なければ`discarded`とする。
6. 削除・一覧取得に失敗した場合は例外として呼び出し元へ返す。部分的に消えても「破棄した」と成功を通知しない。残った世代は次回も確認できる状態にする。

別のアプリインスタンスとのファイル操作を完全に排他にする仕組みは現行IOに無い。この案では、候補の再確認と削除する世代の固定によって新しい世代を消さない。共有ファイルを同時に書き換える問題まで解決したとは扱わない。

### 起動処理

```text
候補を見つける → 読む → 3択を出す
  復元 → loadIntoApp → 成功なら終了
  保留／Esc → 次の候補
  破棄 → discardRecovery
    discarded → 「自動保存を破棄した」→ 次の候補
    changed → 同じ保存先の候補を取り直す
    例外 → 「自動保存を破棄できなかった」→ 次の候補
候補を終えたら、現在の空のプロジェクトの自動保存を開始
```

復元の失敗時の通知と次候補への移行は今の動きを保つ。読めない自動保存を自動で削除することはしない。全候補を終えた場合も、現在のプロジェクトで自動保存が始まることを確かめる。

## 検証と完成条件

| 確認                             | 期待する結果                                                             |
| -------------------------------- | ------------------------------------------------------------------------ |
| 未保存作業を破棄 → 再起動        | 同じ作業の復元確認が出ない。古い世代も復活しない                         |
| 保存済みプロジェクトの変更を破棄 | 本体・素材・通常のバックアップが変わらず、保存済みの姿勢を開ける         |
| 保留／Esc → 再起動               | 元の自動保存が残り、後から復元できる                                     |
| 復元する                         | 素材と作業を読み、保存先・変更あり・自動保存の開始が今までどおり         |
| 候補が複数                       | 破棄・保留の対象以外の作業は残る。次の候補を復元できる                   |
| 新しい世代が増える／候補が消える | 古い確認で新しい自動保存を消さず、候補の再取得へ進む                     |
| 削除できない／一部削除後に失敗   | 成功と通知しない。残った世代・本体・素材を保護する                       |
| 削除対象以外のファイルを置く     | `project.v*.json`・PNG・任意ファイル・別ディレクトリを残す               |
| 新しい世代が後で書かれる         | 正常な新しい復元確認が出る。永続的に復元を無効化しない                   |
| 3択のキー操作とキュー            | Escは保留、Enterはフォーカス先、選択肢を取り違えず、confirm/promptも動く |

IOの検証はMemoryFileSystemと削除失敗を返す代替を使う。画面では専用の一時プロジェクトと実ファイルを使い、破棄前後の対象一覧と、本体・素材のハッシュが変わらないことを記録する。実ブラウザ／WebViewで3択が小さい窓にも収まり、同じ候補を再起動で聞かないことを確かめる。

「破棄したら再び聞かれない」と「保留した作業は後で戻せる」の両方が満たされたら締める。

## 実装と確認（2026-10-12）

本書の3択と `AutoSaver.discardRecovery` を実装した。破棄はIOの書き込みと直列にし、対象名と保存先、候補の再確認、対象世代の固定、ファイルの事前読み込み、古い順の削除、削除後の候補確認を行う。自動保存名のフォルダを再帰削除しないこともテストした。

新規19件（ダイアログ5・起動処理7・IO7）と既存の関連テスト、全体の回帰・型・lint・整形が成功。本物のWebView2で専用の保存済みプロジェクトを5回再起動し、Escとフォーカスした［後で決める］のEnterは残す、復元は最新の作業へ戻る、破棄は3世代を消し、次回は同じ確認が出ないことを確認した。`project.json`と素材のSHA256は不変、通常のバックアップも残った。別識別子の検証アプリを使い、利用者の自動保存を破棄する操作は行っていない。インストール版の更新は未実施。
