# 再生音声不足の改善と区切り方の比較

後続の修正: 小さい声・発話再開時の音割れの報告に対し、VADの判定用入力と出力ピーク保護を変更した。以下の記録はその変更前のもの。AI生成・プリセットを保った[現行版の検証](../voice-clarity-2026-10-15/README.md)も参照する。

2026-10-15 CO。利用者の「音声不足とは、修正できるか」「短い・長い区間を周期的に使えないか」に対応した。元の品質と区切り方を保ちながらTinyのGPU実行をまとめ、最速75秒、バランス・安定優先各30秒の実機試験で不足0を確認した。[操作説明](../../studio-voice-guide.md)。

## 不足の意味と原因の切り分け

不足は、次の変換音声が再生時刻に間に合わず、再生用の音声が尽きる状態。マイク音量の不足ではない。180ms分の出力を作る処理が継続して180ms以上かかると、一定量のバッファを増やすだけでは遅れが蓄積する。一時的な超過なら、それまでの再生余裕と次の区間での回復が必要になる。

同じPCの未修正版では、実機の最速1区間が約237ms、そのうちAI推論約222ms、雑音処理約13ms、残り約2msだった。開始前の処理を増やす案は約248msで停止が残った。CPUを実際に1スレッドへ変える試験も約1.8秒で不足が出たため採用していない。電源はAC接続だった。GPUの共有負荷等を含む全要因を確定したという意味ではない。

[未修正版](runtime-baseline.json)、[開始前の準備を増やした結果](runtime-warm.json)、[CPU1スレッドの結果](runtime-thread1.json)、[推論・前後処理の計測](diagnose.json)、[AI内部の段階計測](stages.json)。段階計測はGPUの同期を追加するため、通常の処理速度とは分けて読む。

## 短い・長い区間の交互処理

公開JVS音声約6秒を使い、Tiny最速の4ステップ・CFG0・入力履歴1.5秒・生成履歴400ms・参照2秒・同じフィルタで比較した。モデルは同じインスタンスで、各形状を先に準備した。下表の比率は「総処理時間 ÷ 出力する音声時間」。1未満でも実機の処理の揺れ・IPC・再生時計への余裕を別に確認する必要がある。

| 区切り方                      | 平均区間 | 処理時間の比率 |
| ----------------------------- | -------: | -------------: |
| 180ms固定（最初／最後の対照） |    180ms |     1.16／1.33 |
| 120ms・240msの交互            |    180ms |           1.25 |
| 240ms固定                     |    240ms |           0.83 |
| 180ms・300msの交互            |    240ms |           0.87 |
| 300ms固定                     |    300ms |           0.70 |

長い区間を使って回数を減らす効果は観測された。一方、同じ平均長で交互にする優位性はこの短い試験では確認できなかった。短い区間でも履歴・参照・AI生成の共通処理が残り、長い区間の前には収録待ちも必要になる。対照の最初と最後にも揺れがあるため、比率の小さな差を一般的な優劣とは扱わない。[全区間の結果](chunk-comparison.json)、[試験スクリプト](compare_chunks.py)。製品に交互区切りは追加していない。

## 採用した修正

`realtime_graph.py` で、Tinyの同じDiT計算をCUDA Graphへまとめる。計算ごとのCPU/GPU間の実行指示を減らし、固定長の条件から元と同じマスクを作る。マスクの長さをGPUから読み戻す処理はcaptureの外へ分ける。元のモジュール関数はcapture終了時に必ず戻す。

ステップ数、CFG、参照音、区間、入力・生成履歴、FP16、4 CPUスレッド、40msの再生余裕は変更しない。SeedModelとComposerのクラス本体、乱数生成、音響特徴、vocoder、雑音処理、声質、フィルタ、PCM/DAC時刻も従来の経路を使う。GPU待機時の間欠処理は行わない。大型AIとWAV変換には適用しない。

capture時だけ混合精度のweight cacheを無効にして保存領域を保持し、再実行の結果を独立した領域へ返す。最初の試作は再実行時に不正出力を検知して停止したため、そのまま採用していない。[試作の失敗ログ](graph-trial-failed.log)、[修正後の試作](graph-trial.json)。

準備時に元のestimatorとのビット一致を確認する。不一致・非対応の場合は元の処理へ戻す。予期しない入力形状では元の経路を使い、graphのメモリを無制限に増やさない。固定版Tiny・評価モード・FP16に限定する。開発時は `VOICE_DISABLE_CUDA_GRAPH=1` で無効にできる。保存形式と既存プロジェクトは変更しない。

## 元のAI計算との一致

公開音声3秒について、最適化側を実行するたびに、同じ重み・同じ入力テンソルを元のestimatorへ渡して直接照合した。別workerの乱数や初期化差を混ぜない比較である。

| Tiny品質 | ビット一致を確認した生成ステップ | CPUスレッド |
| -------- | -------------------------------: | ----------: |
| 最速     |                               72 |           4 |
| バランス |                               84 |           4 |
| 安定優先 |                               88 |           4 |

全244回で一致し、最終音声も有限・非無音だった。[一致検証](replay-validation.json)、[ログ](replay-validation.log)。検証用の `validate_realtime_graph.py` は両経路を毎回計算するため、性能試験とは分けて実行した。本人の聴感やあらゆる発音の品質保証をしたという意味ではない。

## 実機の連続動作

RTX 4050 Laptop 6GB / Ryzen 7 7735HS、48kHz、Razer Seiren Mini → Sound Blaster Play! 3。公開音声・雑音・無音の周期を実マイク機器の時計で送り、出力は常にMute。マイクPCMは保存しない。全品質で `cudaGraph: 1` を確認した。

| 品質                      | 継続時間 | 最終内部遅延 | 最終処理時間 | 最大処理時間 | 不足・overflow・入力/出力status |
| ------------------------- | -------: | -----------: | -----------: | -----------: | ------------------------------- |
| 最速・180ms/4ステップ     | 75.009秒 |     581.07ms |     103.07ms |     183.63ms | すべて0                         |
| バランス・240ms/6ステップ | 30.003秒 |     684.01ms |     147.64ms |     192.47ms | すべて0                         |
| 安定優先・300ms/8ステップ | 30.006秒 |     816.91ms |     164.40ms |     246.59ms | すべて0                         |

最速は7,502窓・7回、他は各約3,000窓・3回の声質／フィルタ変更を含む。フィルタ全体OFF・最大8個・順序反転等を使い、Muteの非ゼロ出力も0。最速の記録時の内部遅延は約567〜581ms。[最速](live-fast.json)、[バランス](live-balanced.json)、[安定優先](live-stable.json)。これらの窓数は10msの再生コールバックで、AI推論の回数ではない。通話先までの遅延・IPC時間とは分ける。

Pythonの44件は成功。非対応時の元経路への復帰、capture失敗時の再試行抑制、形状変更時の処理、既存パイプ・PCM時刻・フィルタ等を確認した。[テストログ](python-tests.log)。UI・Rust・保存形式は変更していないため、前回の本番実行ファイルを使用し、Python音声リソースを更新する。

## 配置済みアプリの確認

インストール先の音声リソースを更新し、本番GUIから最速品質・実マイク入力・出力Muteで15秒動作させた。不足0・overflow0・解析落ち0、表示の内部遅延615ms・処理85ms。入力/出力は各4機器、検証用APIなし、pageerrorなし。停止と自身のアプリだけの終了も成功した。[本番GUIの結果](installed-live.json)、[ログ](installed-live.log)、[画面](installed-live.png)、[配置hash](installed-hashes.json)。エンジン単体75秒の約567〜581msと、本番アプリの615msは別の試験結果として記載する。

releaseと配置先の実行ファイル、および更新した音声ソースのSHA256一致を確認した。main.lockの所有と接続先PIDの子関係を確認して検証し、利用者のアプリを終了していない。制作プロジェクトと元VoiceChangerの設定も変更していない。

今回の連続試験は75/30/30秒まで。30分安定性、OBS・顔追跡・ゲームを含む同時負荷、通話相手側での遅延、本人の聴感は未確認。元の区切り方での安定性確認を、以前の400ms・約1.2秒設定の30分記録で代用しない。
