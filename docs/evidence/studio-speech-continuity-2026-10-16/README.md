# 文章途中・語尾の途切れと、響きを意識した読み方

2026-10-16。ユーザーの「文章の途中で一瞬止まり、また続く」「語尾でも起きる」という報告への対応。

## 原因と変更

固定1秒の音声をためて始めていたため、生成が実時間より遅い文章では再生が追いつき、途中で1秒分をため直していた。長文の実GPU生成時刻を旧処理へ渡し、途中の再バッファを再現した。語尾には、後処理の短い残りPCMと完了通知を別々に渡す経路もあった。

- `speech_buffering.py`: 文章長と同程度の長さの発話の読み上げ速度から総時間を見積もり、今回の区間ごとの生成速度で開始前の余裕を調整する。冷間のモデル読込・最初の生成待ちは区間速度に含めない。単発の遅い区間や、短い返事の間の多さを長文全体に当てはめて過大に待つことも避ける。
- 生成workerがPCMを作った時刻を伝える。受信キュー・再生リングが満杯になった待ち時間を、生成速度と取り違えない。生成済み下書きの送信でも、それまでの計測を引き継ぐ。
- 8秒を超える開始余裕は、既存の最大120秒内のRAMで準備する。有限リングを満たしたまま開始条件へ到達できなくなる状態を避ける。停止はこの準備中にも有効。
- 後処理の最後のPCMと完了は同じイベント。リングへの最後の追加と終了フラグも同じロック内で確定する。保留PCMがあるうちは終了しない。
- 予想外の不足では残り5msを滑らかに減衰し、再開時も5msで戻す。PCMの順序・個数は保持する。正常な連続再生にはこの減衰を入れない。読み上げのデバイス余裕は40msとした。
- 高負荷の結合試験で口解析へ通知するDAC時刻の逆転を検出した。コールバックごとにPython処理開始時刻から換算する方法をやめ、ストリームを開いた際に機器時計と単調時計を一度対応付ける。以後は機器が通知した出力予定時刻を使い、Pythonの実行遅れを再加算しない。音声PCMを時間合わせのために伸縮する処理ではない。

## 同一音声・同一生成時刻による比較

RTX4050 Laptop 6GB、固定版Qwen Base 1.7B、同じ参照WAV・seed・後処理。文章は「今日は、みんなに大切なことを伝えたいです。いつもそばにいてくれて、ありがとう。みんなのことがすきです。」。音声出力機器を開かず、実GPUでPCMと生成時刻を採取し、実製品の再生コールバックを10ms単位で動かす。開始前の量だけを旧／新で変える。最終再計算は保存したPCM24から行う。

| 読み方 | 音声長 | 生成時間 | 旧方式の途中待ち | 修正後 | 修正後の出力開始 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 文脈に合わせる | 7.68秒 | 8.79秒 | 1回 | 0回 | 3.07秒 |
| 大切なことを伝える | 8.32秒 | 9.58秒 | 1回 | 0回 | 3.14秒 |

数値は[continuity.json](continuity.json)。比較音声: [修正前の待ちを再現](before.wav)、[修正後](after.wav)。比較は同じ「大切なことを伝える」のPCMで、生成内容の違いによる比較ではない。旧方式の出力尺9.75秒に対し、修正後は元の8.32秒となり、語尾まで消費した。

## 響きを意識する指示

［文脈に合わせる］に、重要な言葉は会話の音量のまま芯・自然な響きと丁寧な置き方、話題の切り替えは短い間と明瞭な出だしを意識する条件を加えた。メインと別入力窓に［大切なことを伝える］［話題を切り替える］を置き、既存の［場面・話し方］へ指示を反映する。選択後は自由に編集でき、既存の設定形式で保存する。

参照声・話者プロンプト、声質調整・出力ゲイン・フィルタをこの選択で変えない。声を低く作ることや、大声を指示しない。これは合成モデルへの話し方の条件付けで、音響的な響きを数値指定する機能ではない。BaseのモデルカードはInstruction Controlを対応機能として掲載していないため、既存の`instruct_ids`経路での追従には限界がある。生成が変わることと、意図通りの響きになることは区別する。[Qwen Baseの公式モデル説明](https://huggingface.co/Qwen/Qwen3-TTS-12Hz-1.7B-Base)。

[指示を加えた生成例](delivery.wav)を保存した。話者の参照hashは両例とも`dac5a689fe406465a88b481d085ae4fa0396adc9baeda044c93913df39ed039d`。自然な例のRMS0.0609、指示例0.0693（約1.1dB差）は生成に伴う差で、出力ゲインを上げたものではない。響きや演技の適合は試聴で判断する必要がある。

## 検証と限界

Pythonの回帰試験は、遅い生成で旧方式が不足し修正後に不足しないこと、短い高速発話、8秒を超える準備、先行合成の引き継ぎ、語尾の短いPCMと終了の同時処理、中断とミュートを検査する。実アプリではGPU・WASAPI出力を使い、ミュートした状態で別窓から送信する。実測結果とインストール照合は同フォルダのJSONに保存する。

最終検証: Python92件、関連する画面・サービス44件、実GPUのTauri結合7件が成功。型検査・lint・整形、本番ビルドも成功した。本番の検証フックを除去したビルドを通常のインストール先へ配置し、実行ファイル・音声コード・参照WAVなど11ファイルのhashを照合した（[installed.json](installed.json)）。

- アプリの短文2件は入力→実出力3.120秒／3.083秒、再バッファはいずれも0回（[native-latency.json](native-latency.json)）。生成前の先行完了を待たずに送信した測定。
- 長文の実アプリ試験は8.32秒の音声を12.95秒で生成、開始前に4.475秒分をため、送信→実出力7.219秒、途中・語尾の再バッファ0回。全生成の完了前から再生した（[native-continuity.json](native-continuity.json)）。アプリ描画・出力機器も含むため、前述の生成ログ再生の3.14秒と同じ測定ではない。
- 対象文の全文3回／逐次2回を繰り返し、同じ話者キーを維持（[native-repeated.json](native-repeated.json)）。別入力窓とメインの場面指示の共有を確認した（[画面](input.png)）。
- 最終PCMはミュート時0、有限値、機器時刻に従う通知の逆転0（[native-stream.json](native-stream.json)）。中断後に遅い音声が流れないことと、一時要求の破棄も確認した（[cancel-stream.json](cancel-stream.json)）。

生成の高速化そのものを追加した変更ではない。長い文章・遅い生成では開始前の余裕が増える。開始後のGPU負荷急変や、文章長からの音声長の推定誤差による待ちを完全には保証できない。参照声のhashが同じであることだけで、知覚される声質の完全一致を証明したとは扱わない。
