# 話者固定と入力中の先行合成

2026-10-15。基準モデルの写し・検証専用の識別子・実CUDA GPU・WASAPIのミュート出力で確認した。制作中のモデルを変更せず、起動していたユーザーのStudioを終了していない。GPUはユーザーが解放した。

## 固定するもの

従来は発話ごとにVoiceDesignへ声の説明を渡し、声自体を作り直していた。現在は音声変換の参照WAVと共通の声質設定を使う。Qwen3-TTS Base 1.7B（revision `fd4b254389122332181a7c3db7f27e918eec64e3`）を固定し、同じ参照音声の話者プロンプトを再利用する。参照WAVのSHA256も渡し、読込時に変わっていたら拒否する。

声質・出力フィルタ・ゲインは音声変換と同じ設定で常に適用する。話者条件と、文章・場面・文脈からの読み方の指示を分離した。以前の声の説明による発話ごとの再設計は行わない。参考: [公式のVoiceDesign→Cloneの使い方](https://github.com/QwenLM/Qwen3-TTS#voice-design-then-clone)、[公式Baseモデル](https://huggingface.co/Qwen/Qwen3-TTS-12Hz-1.7B-Base)。

## 入力から送信まで

両方の入力欄を監視し、IME確定後450msでその時点の全文を生成する。未入力の続きを推測しない。GPUジョブは一つだけで、変更が重なった場合も最新候補一つを保持する。古い下書きは協調停止し、生成結果を再生へ渡さない。

送信時は文章・文脈・参照声・声質設定が完全一致する結果だけを再利用する。全文が準備済みなら即再生し、同じ入力を生成中ならその処理を引き継ぐ。全文方式では完成を待ち、逐次方式では既存の先頭部分から再生する。次の文章の入力や入力欄の消去は、送信済みの発話を取り消さない。

## 結果

- Python76件、関連デスクトップ44件、実機結合4件が成功。TypeScript本体／e2e、変更したTypeScriptのESLintも確認。
- 実機でIME変換中は生成しないこと、編集後の最新文章を採用すること、送信前のPCM出力0、履歴0を確認。準備済み音声は送信から再生状態へ116ms。実出力398フレームはMuteで全て0。
- 続く別文章を逐次生成中に送信して処理を引き継ぎ、両発話の`speakerKey`が現在の参照WAVのhashと一致した。未送信の次の下書きを入力・消去しても発話を中断しなかった。
- 既存の全文／逐次切替、別窓の単一起動・開閉・再接続、停止、設定保存も実GPUで再検証した。
- 異なる2文章・読み方を生成し、同じ話者プロンプトを再利用した。同じモデルの話者エンコーダーで、参照とのcosine類似度は0.992／0.980、文章間は0.984だった。BF16による同一エンコーダーの補助指標であり、人間の聴感や独立した話者判定の代わりにはしない。
- 先行結果はRAMだけで保持し最大120秒。ワーカー受信8イベント、再生リング8秒。古い世代、別の入力欄の破棄、場面・文脈・声質・参照声の変更も単体検証した。

## 性能と限界

実機の最初の4秒音声は生成15.01秒、最初のPCMまで1.91秒、初回モデル読込20.03秒。次の3.28秒音声は生成12.49秒、最初のPCMまで1.42秒、再バッファ2回。先行生成で送信後の待ち時間を減らすが、生成速度自体が実時間に追いついたものではない。116msは事前に生成が完了していたケース。

Baseへ参照声と抑揚の指示を与えているが、場面への適合、長文の安定性、音声変換出力との聴感上の一致、OBSを含む配信全体はミュート試験だけでは評価しない。音声変換と合成は異なる方式なので、完全に同じ波形を出すものではない。
